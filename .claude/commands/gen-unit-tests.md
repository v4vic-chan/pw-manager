# 任務：產生功能模組單元測試

## 用詞與原則說明
單元測試與跨層邊界測試（`/gen-boundary-tests`）性質不同：
單元測試的目的是「先寫測試釘死行為規格，再由實作端讓測試從失敗（紅）轉為通過（綠）」，
屬於 Test-Driven 開發的標準流程。因此本指令產生的測試**預期在對應實作完成前會執行失敗**，
這是正常且必要的狀態，**不得**比照邊界測試使用 `test.skip` 迴避，除非該測試依賴的是
其他尚未定義的資料契約或型態（而非單純尚未實作的函式本身）。

## 目標檔案
規格檔案路徑：$ARGUMENTS
若未指定路徑，預設在 `specs/` 目錄下尋找唯一的規格 .md 檔案。

## 執行步驟

1. 讀取目標規格檔案，定位標題文字包含「功能模組規格」的章節
   （**不要**依章節編號定位，只認標題文字），取得該專案定義的所有功能模組
   （子章節數量與名稱依專案不同而異，不得假設固定數量）。

2. 讀取標題文字包含「驗收標準」或「Acceptance Criteria」的章節，交叉比對
   每個功能模組是否有對應的驗收項目；若某模組完全沒有對應驗收標準，
   仍需依模組描述本身合理推導可測試的行為，並在測試檔頂部註明
   「此模組於規格中缺乏明確驗收標準，測試依模組描述自行推導」。

3. 讀取標題文字包含「資料契約」或「Data Contracts」的章節，確保單元測試
   使用的輸入/輸出資料結構與型態定義檔（`src/types/` 下對應檔案）一致。

4. 針對每個功能模組，產生對應單元測試，需覆蓋：
   - 正常路徑（happy path）：符合規格描述的標準輸入應產生預期輸出。
   - 邊界條件：規格中明確提到的數值邊界（如長度上限、重試次數門檻）。
   - 異常路徑：規格中提到的錯誤處理邏輯（如驗證失敗、格式錯誤）。
   - 若模組描述涉及狀態轉換（如 2FA 開關、登入鎖定倒數），需測試狀態
     轉換的前後一致性，不能只測試單一時間點的結果。

5. 依專案現有技術棧與既有測試框架撰寫測試語法（沿用專案既有測試框架設定，
   不重新詢問；若專案尚未有任何測試框架記錄，依序參考規格 §2.1 技術棧選型
   與既有專案設定檔判斷，仍無法判斷才詢問使用者），測試檔存放於
   `tests/unit/` 下，命名格式為 `<模組名>.test.ts`（或對應語言慣例）。

6. 測試檔生成後，執行測試並如實回報結果：
   - 尚未有對應實作的模組，測試預期為失敗（紅燈），此為正常狀態，
     不視為錯誤，不得為了讓測試「先通過」而反向簡化測試內容。
   - 若某測試因型態錯誤或語法錯誤而失敗（非因缺少業務邏輯實作），
     則視為此指令產出的錯誤，需修正至僅因缺少實作而失敗為止。

7. 完成後，列出本次產生的測試檔路徑、涵蓋的功能模組清單，以及測試執行
   結果摘要（區分「因缺少實作而失敗」與「其他錯誤」兩類）。

## 限制
- 僅依規格內容產生測試，不得在測試檔內一併撰寫功能模組的實際實作。
- 不得修改規格文件本身。
- 不得自行新增規格未定義的功能行為或驗收條件。
- 不得使用 `test.skip` 迴避因缺少實作而導致的測試失敗。
